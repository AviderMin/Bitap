# Bitap 项目审查、产品差距与开发执行报告

日期：2026-11-08（北京时间）  
审查基线：`54bc9f3`，Android / Kotlin / Compose，当前版本 0.1.0。  
用途：交给后续 AI 开发者作为问题清单、技术决策依据和阶段验收合同。

## 1. 核心结论

Bitap 已经有可继续开发的工程基础，但距离能长期设为默认输入法还有明显差距。主要问题是拼音解码与排序泛化不足、纠错覆盖窄、连续中英混排缺位、触控与编辑效率缺少用户验证，以及本地大模型资源成本过高。

下一阶段应定位为：**离线、隐私优先、中文基础输入可靠的 Android 输入法**。首先让用户不必反复选词、退格、切语言；AI 作为可选增强层，基础中文输入必须在无模型时同样可靠。

建议开发投入顺序：输入正确性与测量体系 → 引擎方案对比 → 拼音/纠错/混排 → 触控与编辑工具 → 兼容性与性能 → 可选 AI。暂停新增主题、动效和没有真实使用收益的 AI 功能。

不能把测试通过、功能存在、工程交付完成等同于产品好用，也不能仅根据现有小评测集宣称达到商用输入法水平。

## 2. 审查范围与证据可信度

本次阅读了输入法服务、控制器、状态机、文本会话、拼音引擎、触控实现、用户词库、设置、本地 AI 服务、构建配置、评测脚本与历史交付/设备报告。执行结果见第 15 节。

证据分三类：

- **本次源码核查**：可确认架构、参数、功能边界和潜在风险，不能代替实机复现。
- **仓库历史实测**：引用 2026-11-07 的质量和设备报告，注明当时口径，不冒充本次重新测量。
- **开发建议/假设**：包括目标值、时间估计、根因推断和路线选择，需要通过实验确认。

本次没有操作手机，也没有对搜狗、百度、Gboard 等进行同机盲测。竞品官方资料只能证明其公开能力，不能证明其当前版本的准确率、延迟或隐私表现。未检查所有函数的每条分支，不将本报告表述为无遗漏的安全审计。

## 4. 已有量化证据：为什么不好用

以下均来自历史 `FINAL_DELIVERY.md`、`SEALED_EVAL.md` 和 `DEVICE_PERFORMANCE.md`，不是本次设备新测。

| 指标 | 历史结果 | 对体验的含义 |
|---|---|---|
| 封存集引擎可评分首选 | 51/105，48.6% | 在该样本中约一半不能直接选首项；不能外推成所有真实输入的错误率 |
| 封存集引擎可评分前五 | 78/105，74.3% | 部分输入需要更深候选或重新拆分 |
| 自然长句首选 / 前五 | 4/22、12/22 | 长句直接输入缺乏可靠性，4/22 约为 18.2% |
| 错拼首选 / 前五 | 11/22、12/22 | 候选召回短板明显，单纯调整显示顺序不够 |
| 开发 / 保留集引擎首选 | 79.0% / 66.4% | 与封存集 48.6% 差距大，存在泛化不足；数据分布也不同，不能直接断言训练泄漏 |
| 显式切换中英文 | 历史真机验收通过 | 能手动切语言，不代表支持自然连续混排 |
| 按键到 DisplayPresent p95 | 64.6ms，142 帧样本 | 完整可见反馈比应用侧帧完成 p95 17.6ms 慢，不能只报后者 |
| 连续输入 jank | 历史工具口径 68% | 是排查信号；须核查刷新率、deadline、trace 和帧归属，不能说“68% 按键卡住” |
| 无 AI fresh 进程 PSS | 65,159KB | 基础进程已有相对轻量的起点 |
| AI 生成峰值 PSS | 1,793,781KB，约 1.71GiB | 模型约 328MiB 不代表运行时只耗同等内存 |
| 生成后 18 秒 PSS | 约 1.72GB（历史报告口径） | 内存回落不足，输入法长期驻留时成本高 |
| 设备范围 | 单一型号 / Android 16 | 无法代表所有 Android 13+ 与 ROM |

历史 `avgTaps` 实际是“候选名次+1，前五未命中记 9”的代理指标。它既不是字母按键总数，也不是屏幕上真实点选次数。应保留历史可比性，但改名为 `rankCost`；新增真实操作计数，避免继续用误导性名称。

## 6. 代码层面的关键发现与开发要求

### F01：自研解码器已到“需要换评估方法和模型”的阶段（P1）

依据：`PinyinEngine` 同时承担词典索引、音节切分、简拼派生、lattice 搜索、纠错、排序和用户学习，存在大量手工分值、beam 和候选配额。历史扩大 beam 后长句改善有限，质量与延迟存在交换。

推断：覆盖、语言模型、剪枝和候选展示共同决定体验，继续局部加奖励可能产生类别间回退。不能归因成“词库小”一个原因；README 的“约 3 万条”也与历史资产统计 65,999 条不一致，应由生成脚本输出统一统计。

要求：把召回、搜索剪枝、排序、候选保留和实际选词操作分开测量。所有调参先报告正确路径是否存在；不在候选池中时先解决召回，再做重排。拆出可替换引擎契约，保留当前实现作 baseline。

### F02：纠错不是完整输入噪声模型（P1）

依据：`collectCorrections` 只接受长度 2–12 的查询；存在正常候选较强时不触发、已有两字及以上 exact entry 时跳过的分支。替换字母统一枚举，未使用触点坐标、邻键距离或个体误触分布。

影响：长串中只错一个字母可能没有纠错路径；错误拼音碰巧命中另一词时，正确意图也可能无法进入候选。

要求：构建分段拼音图上的局部编辑代价；保留原始候选与 raw 输出；将邻键纠错、漏字、多字、交换、模糊音分为不同特征。纠错必须可撤销，不能因为结果看似高频就无提示改掉英文或专名。

### F03：查询接口缺少常规中文上下文（P1）

依据：常规 `search(input, limit, shouldContinue)` 的输入没有编辑器前文、已选片段或领域提示；它有词内/句内统计和本地学习，但不等同于利用已上屏前文。AI 入口另有有限上下文读取。

要求：新增受限、内存态的 `QueryContext`，按密码/隐私策略决定是否可读，包含少量已提交前文与当前分段信息；不能记录整段输入历史。先验证上下文特征对同音词和分段连续输入的收益，再考虑小型神经重排。

### F04：触控策略需要验证双拇指滚动输入（P1）

依据：`KeyRowPointerTracker` 已支持多指，`handleUp` 执行提交；源码明确采用抬起顺序。按行识别触控，位置变化会重选当前键，并存在移出区域取消规则。

风险假设：当 q 先按、w 后按，但 w 先抬，可能提交 wq；跨行滑动与视觉间隙也可能影响目标键。该策略并非自动构成 bug，但“多指测试通过”不能证明快速打字顺手。

要求：增加带时间戳的 down/move/up 回放，覆盖交叠按压、跨行、边缘、长按中第二指和系统 cancel。对比按下顺序、抬起顺序及缓冲提交方案的误序/误触率。触控事件只在受控实验中使用合成数据或经同意的本地数据。

### F05：AI 关闭取消请求，不等于释放运行时（P0）

依据：`KeyboardController.onSettingsChanged` 在 AI 关闭时调用 `cancelAi()`；`DefaultAiRewriteService.cancel()` 主要取消请求；引擎 `release()` 出现在删除模型、导入替换等路径。`LiteRtQwenEngine` 缓存 CPU Engine。历史设备报告确认生成后内存长期偏高。

要求：区分“取消本次生成”“关闭 AI”“卸载模型”“终止推理服务”。关闭 AI 应进入可测量的卸载流程；取消与 close 的并发必须串行化，避免一边 native 推理一边释放。若库关闭后仍保留大量内存，实验性采用独立非导出 `:ai` 进程和绑定服务，使用最小 IPC 请求、请求编号及死亡恢复；不要终止 IME 主进程。

进程拆分是候选方案，不保证立即解决性能；需量化 IPC、初始化时间和残留内存。默认无模型时不得初始化 native 推理引擎。

### F06：功能叙述与生产入口仍需统一（P1）

依据：实际 AI 入口是拼音词库候选；仓库还保留 RewriteTone、rewrite 服务和面板相关实现，产品简报开头有润色叙述，后文又明确不提供改写。

要求：建立唯一能力清单，区分已发布、实验、未接通。没有生产入口的代码不能算产品能力。当前优先统一成“AI 拼音候选”；改写若未来需要，单独定义选区、预览、应用、撤销与过期检测流程。

### F07：学习能力已有，但容量和学习单位需要验证（P2）

依据：`MAX_USER_ENTRIES=200`，按词与拼音记录次数，有上限、衰减和清除 generation；不能误报为无学习或清除必然失效。

要求：用不含真实隐私的 1,000 条合成学习事件验证淘汰、同音词、重启和清除。研究跨分段造词，避免只记住单次候选；提供删除单词入口。先测实际学习价值再调整容量，不以无限存储代替算法改进。

### F08：工程验证偏向“能运行”，产品验证不足（P0）

依据：已有大量 JVM 测试和设备脚本；本次文件清单未见 `androidTest` 实机测试集或仓库 `.github` CI 工作流。`scripts/verify.ps1` 主要执行单测、debug 构建和权限校验，并未覆盖全部产品体验门槛。

要求：新增可复用的实机测试宿主，包含原生 EditText、Compose TextField、WebView 和不同 EditorInfo 字段；记录最终编辑器文本、选区、composing 和按键序列。把测试 APK 与受测 release hash 绑定。基准测试与 correctness 分开运行。

### F09：兼容范围与依赖预算要明确（P2）

依据：`minSdk=33`、仅 `arm64-v8a`；LiteRT 为主应用实现依赖；本次 Gradle 输出有 built-in Kotlin / 旧 DSL / variant API 弃用警告。

要求：明确当前只面向 Android 13+ arm64 用户，不把这个范围称为普遍兼容。先保持可构建，再单独安排 Gradle/AGP 迁移；评估 core 与 AI 构建变体的包体收益。降低 minSdk 和扩 ABI 必须依据需求与设备成本，不能和引擎重构混在同一次提交。

## 7. 引擎路线：先做对照实验，再决定重构深度

推荐方向是保留现有 IME 外壳，隔离输入引擎。默认不批准整仓重写，也不预先承诺 librime 一定更准。

| 路线 | 优点 | 主要成本 | 决策方式 |
|---|---|---|---|
| A. 演进自研 Kotlin 引擎 | 保留现有测试和可控性 | 数据、排序、纠错与维护均需长期投入 | 作为基线，设质量和时延止损线 |
| B. librime + 经审核的拼音方案/词库 | 可利用成熟引擎与方案生态 | NDK/JNI、配置部署、词库许可、包体和候选行为适配 | 制作最小 Android PoC，与 A 同集同机对比 |
| C. 紧凑统计/小模型重排 | 可对上下文与整句排序补强 | 合法训练数据、训练评估、量化与设备预算 | A/B 的召回足够后再实验 |
| D. 大模型每键解码 | 理论上可用语义 | 延迟、内存、功耗、幻觉与可预测性成本 | 当前排除生产主链路 |

引擎抽象至少表达：`sessionId`、`compositionVersion`、原始输入、分段边界、上下文策略、候选文本、消耗的输入范围、候选来源与纠错标记。候选点击时校验所属会话与版本，禁止旧结果替换新输入。

建议契约（概念示例，实施前与现有 reducer 对齐）：

```kotlin
interface InputEngine {
    suspend fun query(request: QueryRequest): QueryResult
    suspend fun learn(event: SelectionEvent)
    suspend fun clearLearning()
    suspend fun close()
}
```

原则：引擎只产出候选和消费范围，文本写入仍通过 Controller/TextSession；引擎不得直接访问网络、系统剪贴板或任意编辑器内容。librime 等 native 调用需明确线程归属、会话释放和崩溃恢复。

引擎实验输出质量、设备 p95/p99、冷启动、PSS、APK 增量、许可清单、集成复杂度。若 B 的质量不优或成本过高，记录结果继续 A；若 A 连续两轮无法在新数据上获得有意义提升，停止增加特例，重新评估 B/C。

## 8. 目标体验规格

### 8.1 中文输入

完整拼音、简拼与混合拼音均有明确规则；显示可理解的音节/分段，支持先选前半句再继续；候选第一项稳定，避免结果更新时用户点到另一个词。输入过长时分段或给出可操作提示，不能让现有 64 字符搜索上限表现为突然没有中文候选。

### 8.2 连续混排

定义一套明确的保留规则：全大写缩写、邮箱/URL、数字与单位、常见英文词和代码标识符。歧义时提供中文与 raw 两路候选；不要擅自把所有小写英文字母判为英文。手动中英切换、回车、空格、标点、选区和退格都要有确定语义。

### 8.3 触控与反馈

键盘高度与底部留白分别调整；候选展开不遮挡正在编辑的关键行；关键键的有效命中范围可解释。声效与震动按用户设置执行。候选、按键和装饰层的重组范围分别测量，用 trace 决定优化点，不能仅凭“Compose 慢”就重写为 Canvas。

### 8.4 编辑工具

先做空格拖动光标、删除加速、常用符号和撤销，再考虑丰富表情/剪贴板历史。长按删除按用户可见字符或词边界处理；密码场景禁止学习与 AI 上下文。剪贴板读取由明确动作触发，默认不持久化内容。

### 8.5 安装与设置

首次安装先完成启用 → 选择默认输入法 → 本地试打。模型导入放到可选增强项。提供用户词库关闭、清除、单词删除、隐私输入开关与明确反馈；先实现简单可靠的设置，不再叠加主题系统。

## 9. 评测体系重建

### 9.1 数据集

现有 dev/holdout/sealed 均保留用于历史比较。sealed 已经公开入库且报告已可见，对未来开发者不再是严格盲测材料，下一轮必须另建未见验收集；不得把旧集反复运行称为新的封存验收。

建议新建开发集至少 1,000 条、独立验收集至少 500 条（规划值），按日常聊天、工作表达、同音歧义、长句、简拼、错拼、连续混排、数字符号、专名分别分层。按句子来源和近重复簇切分，不能只随机切行。公布每类样本量、置信区间、数据来源与许可；允许多个正确答案，人工复核歧义。

另建事件序列集，输入包含按键、选词、删除、光标、切应用和旋转事件；期望是完整最终文本与状态。纯拼音引擎不支持的邮箱/混排交互不能混进引擎准确率分母后只报一个总数，但必须保留为端到端失败项。

### 9.2 指标

- 引擎：Top1、Top5、完整覆盖率、正确路径 oracle、每类错误率和 `rankCost`。
- 实际输入：每百字修正操作、退格、展开候选、选词、语言切换、任务完成时间、最终字符错误率。
- 体验：试用者能否连续一周保留为默认输入法、切回旧输入法的原因；小样本反馈不伪装统计结论。
- 性能：输入事件到视觉反馈 p50/p95/p99、候选刷新耗时、丢帧 deadline、冷/热唤起、PSS/native、耗电与温升。
- AI：首次/热启动等待、取消生效时间、释放后内存、结果可用率、相对普通候选减少的修正操作。

### 9.3 建议阶段门槛

以下是待执行的内部目标，并非竞品实测标准，也不是当前已达结果。统一在新数据和固定设备条件下验收。

| 项目 | 0.2 内测目标 | 0.3 默认输入法候选目标 |
|---|---|---|
| 新验收集中文 Top1 / Top5 | ≥75% / ≥90% | ≥85% / ≥95% |
| 自然长句 Top1 / Top5 | ≥50% / ≥80% | ≥70% / ≥90% |
| 连续混排事件正确率 | ≥95% | ≥99% |
| 丢字、重复提交、跨字段写入 | 核心矩阵零复现 | 扩展矩阵零复现；明确样本量 |
| 按键到可见反馈 p95 | 主设备 ≤50ms | 主/次设备 ≤50ms，低端机明确预算 |
| 普通 / 长串候选查询 p95 | ≤10ms / ≤50ms | 不劣于 0.2，并报告 p99 |
| 非 AI 稳态 PSS | 固定场景 ≤100MiB | 无长期增长，循环后回到预算 |
| AI 关闭后资源 | 若继续提供 AI，10 秒内 PSS 回到基线+100MiB | 所有目标设备达标，否则保持实验功能 |
| 用户操作成本 | 与旧版本相比中位修正操作下降 ≥30% | 同机竞品任务时间差距 ≤15%，需真实对照数据 |

样本过少时不因单条变化调整总方向。任何类别下降超过 3 个百分点或正确性回归，都必须解释并人工审阅；不能仅凭总分提升合并。

## 11. 迭代路线与退出条件

### 阶段一：建立可信基线（约 1–2 周）

完成 D00、D01、D02 的关键风险处理及 D03。产出可回放样例、指标脚本、引擎适配契约和 AI 资源报告。退出条件是能准确回答“哪里失败、如何复现、使用什么口径”，不以界面更新作为里程碑。

### 阶段二：决定引擎并修复基础输入（约 3–5 周）

完成 D04–D08。优先解决未见长句、错拼、混排和快速按键。达到 0.2 质量门槛后发布内测；不达标则继续诊断，不改名称宣称完成。

### 阶段三：达到可长期试用（约 2–4 周）

完成 D09–D14，补齐高频编辑、学习与兼容性；开展 5–10 位目标用户的本地试用和同机任务对照。记录切回其他输入法的具体原因，按最高频痛点修复。

### 阶段四：选择性增强

只有在基础体验稳定后，才考虑紧凑重排模型、下一词联想、英文预测及一种新增布局。是否继续本地大模型，由净操作收益、内存和等待时间决定，不能由“AI 输入法”的名称决定。

总体估计约 6–11 周存在较大不确定性，部分任务可由同一开发者交错安排；native 集成、数据许可和 ROM 兼容性可能拉长周期。以上不代表已授权额外人员或多代理并发执行。

## 12. 设备与实测协议

至少覆盖一台当前主力机、一台 4–6GB 低内存机、一台不同 ROM 的中端机；Android 13、14、15、16 尽量覆盖。真实可得设备不足时如实写“未测”，模拟器只补行为验证。

同机测试固定系统刷新率、亮度、温度区间、构建类型和 AI 开关；记录机型、系统版本、APK hash。性能测量不与编译、录屏或重型调试工具同时进行，必要时分别记录它们的开销。

输入任务同时包含原生输入框、Compose、WebView、搜索、聊天、邮件、密码和数字字段；测试横竖屏、应用切换、系统回收、IME 隐藏/恢复、后台推理、来电/窗口中断与 TalkBack。对每种关键字段至少做一次 composing → 选区变更 → 输入 → 删除 → 提交完整链路。

触控性能使用可回放事件和真实触摸两类数据；ADB 单指逐字点击不能替代双拇指试打。用户试用只保存经同意的汇总与合成复现，默认不导出真实聊天、账号、密码或完整按键历史。

## 13. 风险与决策约束

- **数据资源**：扩大词库前明确逐资源来源、许可证、署名和派生方法；评测句不能反向成为手写生产词条。既有 Tatoeba 资源仍沿用历史记录的许可边界，不重新宣称“可任意商用”。
- **引擎替换**：需要候选消费范围、学习、分段、线程、配置升级和失败降级方案；旧引擎保留回退开关至实机验收完成。
- **上下文使用**：只在允许的字段读取限定上下文，内存态处理；学习条目仍可能含敏感词，提供开关、单条删除和清除，不承诺“任何输入都绝不落盘”与学习行为相矛盾。
- **AI 安全写入**：会话/光标/选区变化、超时、取消后必须使旧结果失效；模型输出始终经用户选择再写入，不能自动发送。
- **维护成本**：每新增一个布局、模型或主题都会扩大回归矩阵；当前优先减少状态分支和功能承诺。
- **测量失真**：JVM 延迟不等于 Android 端到端延迟；单模型文件大小不等于峰值内存；cached Gradle SUCCESS 不等于本轮重新执行测试。
