# Bitap 项目审查、市场对照与改进建议

审查日期：2026-11-13（北京时间）。代码基线：`80de879`，开始审查时工作树干净。本文是该基线的审查快照和研发建议，不替代需求、架构或发布验收规范；历史结论仍保留在原文档和 Git 中。

证据范围：阅读生产输入链路、解码与候选收集、混排、英文预测、触控、编辑器适配、AI 生命周期、设置、构建与评测脚本；复核开发评测和历史设备记录；联网核对竞品官方帮助、政策和开发者应用商店说明。本次没有安装竞品、没有进行竞品准确率/时延/内存对测，也没有运行手机设备测试。公开功能声明不能证明体验优劣。

## 1. 核心判断

Bitap 已有能持续迭代的工程基础：纯 reducer、可替换引擎接口、后台查询、session/version 防陈旧回填、部分消费、本地学习管理和失败降级都值得保留。但中文整句可用性不足，离“每天作为默认输入法使用”仍有明显距离。下一阶段应优先做到少改错、少找候选、可靠混排和稳定触控。

建议定位为：**面向重视隐私的 Android 中文用户，开箱即用、无网络权限、资源可控的离线输入法**。先以全键盘中英混输用户为核心人群。开发者场景可作为专名/代码混排测试入口，但不能只用技术词样例代表中文日常输入。

“无网络权限”是可审计的优势，但不是独有优势：Fcitx5 Android 官方同样声明不要求联网权限。因此，竞争力还必须来自默认词库、输入质量、设置简单、学习可管理和低资源成本。[Fcitx5 隐私策略](https://fcitx5-android.github.io/privacy/)

建议研发顺序：**建立当前体验基线 → 中文候选生成与词选择 → 混排/纠错 → 设备与触控验收 → 个性化和发布体验**。AI 独立设资源门槛，不作为基础输入可用性的依赖。

### 2.1 质量数字应如何解释

当前 D05 开发集共 1,050 条：纯引擎 1,000 条，混排交互 50 条另报。以下为默认参数基线，开发集不是独立产品验收，更不是与竞品同条件对测。

| 分组 | Top1 | Top5 | 含义 |
|---|---:|---:|---|
| 纯引擎全部 1,000 条 | 470/1,000，47.0% | 635/1,000，63.5% | 含简拼等相对容易专项，不宜用其代表自然句体验 |
| 自然句全部 700 条 | 234/700，33.4% | 366/700，52.3% | 包含 33 条超过查询预算的长句 |
| 自然句预算内 667 条 | 234/667，35.1% | 366/667，54.9% | 用于定位排序/生成问题，不可替代全量分母 |
| 短句 300 条 | 142/300，47.3% | 200/300，66.7% | 短句也有较大改进空间 |
| 中句 277 条 | 89/277，32.1% | 152/277，54.9% | 不能只把问题归为极长输入 |
| 长句预算内 90 条 | 3/90，3.3% | 14/90，15.6% | 优先级最高的算法问题之一 |
| 长句全部 123 条 | 3/123，2.4% | 14/123，11.4% | 控制器前缀分段可继续输入，但不等于完整句已命中 |

依据：[评测规范](EVALUATION.md)、[进度第 10、11、29、33 节](PROGRESS.md)。查询时延为宿主 JVM 指标，不能写成手机按键到呈现时延；整句精确匹配也不能等同于“每个字的准确率”。

### 2.2 最有价值的诊断结果

长句 90 条中 oracle64 只有 22 条，Top5 为 14 条。在固定池和当前消费/比较口径下，即使把所有正确候选推到前面，Top5 也只能从 14 增到 22；其余 68 条需要解决候选进入池的问题。

现有路径诊断把 59/90 标为 not-generated，但其中很多样本的 debug sink 已饱和，因此不能把它写成“已证明都是 beam 剪枝”。独立词典切分能覆盖 89/90，说明单纯增加词典条目数量也缺乏充分理由。

现有实验已排除一些低收益路线：单纯 beam64→96/128/192、entries8→16/32，没有带来长句 Top1/Top5 改善；句级 n-gram 重排也无收益。已有 word-count diversity 探测同样未带来 Top1/Top5 改善。下一轮必须提出新的可验证机制，不能再次把“加宽搜索、调权重”当作未试过的方向。

## 4. 具体改进方向

### A. 中文解码：先提高正确路径存活，再做排序

**问题**：长句大量不在池内，短中句同样不足；现有权重和预算扫描已经趋于停滞。生产查询传入 `QueryContext.None`，自研引擎尚未利用编辑器前文；路径内部 n-gram 不应被称为跨提交上下文理解。

**实施建议**：

1. 给每个位置增加仅开发可用的路径计数、剪枝前后排名、词条截断和候选收集原因统计；debug 满额时明确报告“未知/截断”，避免错误归因。
2. 对允许答案做只读受约束路径追踪，回答其边是否存在、何处首次失活、是局部分数还是收集策略丢失。此追踪只用于诊断，不进入生产，也不从验收答案生成词条。
3. 在相同资产上试验“后向剩余代价估计辅助前向搜索”或其他不同于简单加宽的路径保留方法；与现有 word-count diversity 区分。每次只试一个机制，保留时间/分配上限。
4. 候选去重键目前主要按 `word`；检查不同消费范围、纠错来源和完整/分段候选合并是否丢失编辑语义。先构造可重复反例，再决定是否改为包含消费范围的身份与展示去重两层；这是待验证风险，不是已复现文本错误。
5. 有生成收益后，再评估固定候选池的轻量重排、跨提交会话内中文 bigram。后者只使用用户在本次会话提交的有界内容，清楚定义密码/禁学习/切字段清理，不默认读取编辑器正文或落盘。

**建议阶段门槛**：先争取预算内长句 Top5 从 14/90 增至至少 24/90，同时报告全部自然句、33 条超预算输入、成功→失败转换和时延。这个数是研发目标，不是预测或商业可用标准。独立验收不凭开发集涨分替代。

### B. 候选与长输入：优化完成任务的总成本

**问题**：最多 64 项候选、分页、partial 和滚动的组合会增加查找成本。前缀分段避免长输入被拒绝，但固定 64 不代表用户想在此处分段。旧实验已显示简单切短和 partial 重排收益不足。

**实施建议**：

- 先冻结算法，测首屏实际可见正确候选比例、完整长句完成率、候选展开/滚动/翻页次数和误选后恢复成本。
- 在输入串中清楚展示候选将消费的范围、剩余拼音和分段状态；确认长文本省略后仍能区分候选。
- 比较当前“看分段”跳转与明确的分段候选入口，保留整句/分段来源和取消路径；不可只用 Top8 改善宣布体验提升。
- 扩展 65/70/100/200 字符、连续选两三段、选后退格、旋转和光标移动测试。边界策略变化必须与候选布局变化分开实验。
- 保留用户已经选择的空格下方光标手势，不擅自改入口；增加首次提示、编辑页可见替代入口，并单独验证紧凑模式。

**验收**：相同文本的成功完成率不降，成功任务的候选浏览操作中位数建议降低至少 20%；同时报告失败/放弃样本，防止只统计容易成功的句子。

### C. 中英数字混排：从“后缀补充”走向多片段编辑

**代码限制**：[MixedInputResolver](../app/src/main/java/com/bitap/keyboard/core/MixedInputResolver.kt) 只尝试中文前缀 + 一个规范英文/纯数字后缀；英文依赖手写词表；存在完整 CJK 解码时混排解释整体退出。它能防止劫持普通拼音，也可能压掉用户想要的英文解释，不能一刀切反向修改。

**实施建议**：引入有界 token/segment 模型，统一表示拼音、英文原文、数字、连接符和符号，保留原始偏移与大小写。先支持显式选择英文片段并继续中文，再评估自动识别；允许用户纠正分段。URL、邮箱、代码、版本号优先保留 literal；不要将任意字符串规范化为词表中的品牌拼写。

新增开发场景如“周五用 Figma v2.3 改 UI 再发给小王”“预算 2999 元，型号 X200”“foo_bar-v2”“name@example.com”。必须覆盖中文→英文→数字→中文，以及中间插入、选区替换、退格跨片段、撤销和切字段。

**验收**：单列混排端到端最终文本成功率、模式切换数、大小写/标点保留；D05 mixed_en50 仍作为交互集，不把前缀命中当最终文本正确。先做规则完整性，再扩大词表。

### D. 纠错：从短串编辑距离走向保守的局部恢复

生产轻量纠错长度上限 12；新局部窗口实验默认关闭，现有 dev 上还造成自然句回退。当前 typo100 全在短串范围内，不能验证长串局部错拼。

建议新建来源隔离的长串邻键、漏字、多字、交换、模糊音数据，并包含无错误句、专名、代码/英文负例。优先把纠错候选作为明确标记的可选项，保留原文和一键撤销；错误概率、修正代价、语言合理性共同评分。触点偏差模型待实际匿名/同意的本地触点测试后再做，不擅自新增遥测。

模糊音与触控错拼分开：前者给出 n/l、an/ang 等用户可控规则，后者依赖键位和编辑路径。建议误纠正率先设 ≤0.5% 的目标，但样本量必须足以解释置信区间；小样本零误纠正不能证明达到该值。

### E. 触控、无障碍与编辑器兼容

行级多指设计和语义按钮已存在，应保留。当前以抬起顺序提交；双拇指交叠、跨行移动、同帧多指和 cancel 的真实行为需要设备验证，不能仅凭纯 tracker 单测判断快打体验。

建立时间戳事件回放和真实双拇指任务，分别记录漏字、重复字、顺序错误、误长按和修正次数。首批兼容矩阵覆盖 Android 13 与 16、AOSP/Lineage 与至少一个厂商 ROM；原生 EditText、Compose BasicTextField、WebView 和至少一个常用聊天应用。字体 100/130/150%、竖横屏、手势导航和 TalkBack 分开验收。

编辑器侧重点为组合结束回调、选区失效、宿主拒绝操作、长文本全选、密码/禁学习、多行回车和切应用。近期多次 InputConnection 边界修复表明这部分值得设备合同测试，后续不要只增加 FakeTextSession 断言。无障碍应测试聚焦、朗读、触摸探索、候选翻页、长按替代操作，而不仅是有没有 contentDescription。

### F. 个性化、英文与本地数据控制

中文 200 条用户容量对长期专名输入可能不足，但不能直接把容量放大十倍作为效果改进。先测容量淘汰、重启保持、重复学习、误词撤销和分段造词。引入频率/最近使用/用户固定条目分层，并保持删除、关闭学习和清除的 revision/generation 原子性。

建议先提供离线自定义短语和词库搜索/固定/删除。导入导出使用系统文件选择器，明确导出文件包含个人词条，提供格式/版本与恢复校验；不引入账号同步。

英文当前主要是前缀补全与相邻词计数。先测常用词、缩写、撇号、大小写、专名、撤销补全、移动光标后前缀失效，再决定是否扩词库和加入有界拼写纠错。衡量每任务击键节省、错误接受率和用户主动接受率。英文 bigram 即使不保存整句，也可能含敏感相邻词；隐私页应准确说明保存内容。

### G. AI 与资源：让基础输入有独立预算

历史 AI 峰值 PSS 约 1.9GB，且关闭后不同场景释放结果不一，这仍是产品风险。主动点击和延迟加载值得保留；模型损坏、加载失败、低内存和取消都必须保证基础键盘继续可用。

本次审查读取了本地已有 APK（不是本轮 release 构建）：debug 109,573,786B；未签名 release 28,400,044B。release 内 `liblitertlm_jni.so` 为 22,692,856B，约占包体 79.9%。这说明仅取消模型权重分发并不能消除 AI 运行时包体。旧 release 产物的提交归属未重新认证，不据此宣称当前正式发布体积。

建议做基础版/含 AI 版构建实验，用相同源码和 release 配置比较体积、启动、PSS 与维护成本；先验证收益再决定产品分发。若 native 卸载仍无法稳定回收，再评估独立进程与 Binder 的取消/销毁契约。功能关闭、逻辑取消、native 释放和 PSS 回落是四个不同指标。

默认 `aiEnabled=true` 但无模型不初始化；建议实测无模型时 AI 入口的空间和引导收益，避免其挤占中文候选。没有质量收益和资源证据之前，不把 AI 改写、云 AI 或常驻推理加入主输入链路。

### H. 工程、性能与来源治理

- 大文件已集中：PinyinEngine 2,407 行、KeyboardScreen 1,981 行、Controller 1,408 行、Reducer 1,277 行（该基线）。按词典索引/搜索/收集/学习、候选面板/触控/布局、编辑/查询/英文协调逐步抽取；每批保持行为等价，避免整仓重写。
- `collectLattice` 存在前后两次 partial 路径遍历，使用不同分数并经相同 collector 合并。先诊断最终哪些条目被替换、是否仍有必要，再单独消融；不能未经验证直接删循环并称为无行为变化。
- 追加可自动执行的 CI：单测、lint、debug/release 构建、权限、文档和数据检查；签名发布保留独立门禁。把耗时诊断与必要回归分层，冻结验收继续显式 opt-in。
- 在相同设备测按下→按键反馈、按下→候选可用、确认→编辑器呈现三条时延，报告 p50/p95/p99、冷/热启动、热状态、帧时限和丢键。不能用 JVM 查询 5ms 替代端到端 50ms。
- 建议首轮资源目标：常规热输入可见反馈 p95≤50ms、候选更新 p95≤80ms、连续 30 分钟无文本丢失/ANR。它们是待设备验证的工程目标，不能当作已达标或行业标准。
- 生产 detailed 原件缺失、严格来源检查覆盖有限，普通 verify PASS 不等于全部生产数据已严格溯源。发布前补齐匹配 hash 原件、生产资产可重建记录和署名；无法补齐时另起新版本替换资产并重新建立质量基线，不伪造历史来源。
- README 的“518 项”与后续进度、市场文档的 D07 状态、文档索引的旧 HEAD 已不同步。建议自动生成当前验证摘要，历史过程留在进度，避免将旧状态作为当前事实。

## 5. 引擎路线与新增功能的取舍

继续保留 `InputEngine` 边界，自研与 Rime 的比较应同时做两组：同词表隔离机制差异；各自真实可用方案衡量产品价值。宿主 Rime 结果不能直接推断 Android 时延、内存、学习和部分消费行为。

给自研长句改进设有限实验周期：两轮不同机制、有预先记录的预算与退出条件；若没有稳定端到端收益，再推进 Android Rime 实验变体，而不是无期限调参。迁移门槛包括短中长句与混排改善、学习和删除隐私、部分消费、过期取消、包体与设备预算，且前端无需同步重写。

| 功能 | 建议 | 理由 |
|---|---|---|
| 自定义短语、用户词管理、最近符号 | 较早做 | 离线、成本可控、直接减少重复输入 |
| 双拼 | 核心质量稳定后评估第一种新增方案 | 可复用字母键盘，但仍需独立分段、简拼、纠错语义与验收 |
| 九键 | 有明确目标用户需求再立项 | 需要独立消歧、布局和纠错，不能只换键帽 |
| 中文下一词 | 有界本地实验 | 先定义会话、禁学习和隐私语义，再证明击键收益 |
| 手写、离线语音 | 后置且独立资源评审 | 对部分人群重要，但识别模型、授权、包体和维护投入大 |
| 皮肤生态、贴纸、云同步、AI 写作套件 | 当前不列入主线 | 与当前质量瓶颈和离线产品目标不匹配 |

## 6. 可执行的研发批次

以下是顺序和工作量量级，按单名熟悉项目的开发者估计，不是交付日期承诺。算法探索可能没有可上线收益，应按退出条件止损。

| 批次 | 预计投入 | 交付物 | 退出条件 |
|---|---|---|---|
| 0 当前基线与文档 | 2–3 人日 | 当前构建/hash、分类质量、设备任务集、资源表、文档状态修正 | 能复现同一套证据，历史与当前分开 |
| 1 长句候选生成诊断 | 5–10 人日 | 有界路径追踪、失败分层、两个新机制对照 | 达到预设收益且负向/时延可接受，或明确淘汰并转引擎 PoC |
| 2 混排状态与局部纠错 | 各 5–10 人日，分批 | segment 规则、独立数据、事件/设备用例 | 文本/大小写/偏移正确，正常输入不被误改 |
| 3 候选与触控设备验收 | 5–8 人日 | 视口/双拇指/编辑器/字体横屏报告 | 真实操作成本改善，关键文本错误为零 |
| 4 个性化与轻量构建 | 5–8 人日 | 词库管理、可恢复导出实验、无 AI 构建对照 | 长期学习不丢失且删除不复活，资源收益可复核 |
| 持续任务 | 每批同步 | CI、来源记录、性能与回归 | 工程门禁通过后，另做产品验收 |

资源分配建议：约一半投入中文输入质量，三成投入混排/触控/编辑器，余量用于性能、来源与发布。AI 新功能在基础输入目标达成前不扩张。

## 7. 如何完成真正的竞品对测

当前公开资料只能支持功能对照。下一步应在同一手机、同一文本和相同熟练度条件下比较 Bitap、一个商业拼音输入法、微信输入法，以及一个配置明确的开源离线方案。

1. 预先冻结公开可分发的任务集：聊天短句、办公中句、长句、专名、真实错拼、混排、编辑任务分别成组。小样本体验研究和精确率评测分开解释。
2. 每款记录版本、渠道、词库/方案、联网模式、学习开关、主题、键盘尺寸、设备温度与刷新率。首次使用与相同练习量后的结果分别报告。
3. 质量对测先比较共同支持的全拼路径；功能范围另表呈现。对于联网产品，明确比较完整在线体验还是能实际使用的断网状态，不把某开关称为彻底离线的证明。
4. 记录最终文本正确率、完成/放弃率、总时间、修正数、候选操作、语言切换和字母击键。对整句同义/可接受表达预先定义规则，避免把合法输出误判为失败。
5. 相同任务做配对比较；5–8 名受试者、随机交叉顺序可发现主要可用性问题，但不能推断整个市场人群的准确率或满意度。
6. 性能用同设备、相同工作负载的系统工具采集，不比较营销页准确率，不把 APK 商店下载体积与本地未签名包体直接排行。
